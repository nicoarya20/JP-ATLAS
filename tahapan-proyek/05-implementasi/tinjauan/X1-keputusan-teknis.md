### D2 — Skala ukuran teks (mekanisme, nilai, breakpoint, ikon)
**Keputusan.**
1. **Mekanisme tunggal:** `createTheme({ scale })` pada `MantineProvider` (`app/root.tsx:101`), nilai dari cookie `mk-text-size` yang dibaca loader root (SSR, tanpa kilatan). Tidak ada `--mantine-scale` yang ditimpa di `html`/`div`, tidak ada `html{font-size}`, tidak ada CSS `zoom`. Cookie memakai awalan `mk-` mengikuti cookie yang sudah ada `mk-sidebar-collapsed` (`app/components/AppFrame.tsx:37`), bukan `pm-` seperti usul R05/R08/R11. Sumber kebenaran tetap `profile.text_size` (S0.a); cookie = cermin untuk SSR, ditulis saat user memilih dan saat login.
2. **Nilai:** `TEXT_SCALE = { normal: 1, besar: 1.25, sangat_besar: 1.5 }` sebagai konstanta bernama (R11 §3.2; bukan 1/1,125/1,25 milik R08 §243). Body 16/20/24 px. Tetap ASUMSI sampai diuji 2–3 lansia (pertanyaan Q2), tetapi satu baris untuk diubah. Enum DB `text_size` = `'normal'|'besar'|'sangat_besar'` (R02 §3 modul 01, CHECK; bukan angka), jadi nilai skala bebas diubah tanpa migrasi.
3. **Breakpoint ikut skala dengan menskalakan `theme.breakpoints`, bukan hook `bp` R11 §3.7 butir 1.** `buildTheme(scale)` mengisi `breakpoints` = default Mantine × `scale` dalam `em` (`xs 36em, sm 48em, md 62em, lg 75em, xl 88em` × skala). Aturannya: "keputusan tata letak dibuat atas lebar efektif = lebar layar ÷ skala".
4. **Ikon & px:** semua kode BARU memakai `size="1.25em"` (ikon `react-icons`) atau ukuran Mantine (`size="lg"`), tidak ada `size={16}` angka; `h`/`w` tetap diganti `mih`/`maw`; numeric style prop Mantine sudah ikut skala (lewat `rem()`).
5. **Cakupan:** skala berlaku global (satu provider). Layar `/dev` & `/dashboard` lama tidak diaudit di S0–S2; ikon px-nya akan relatif kecil pada 1,25/1,5 (kosmetik). Audit kedua area = ditunda.

**Bukti.**
- Mekanisme: R08 §3 baris 243 sendiri menyebut menimpa `--mantine-scale` pada `div` TIDAK bekerja dan menyuruh `theme.scale`; R05 §3 butir 6 dan R11 D3 (baris 53) sepakat. Jadi "asumsi R08 (--mantine-scale di html)" sebenarnya sudah dikoreksi R08 sendiri; yang berbeda hanya NILAI skala. Kode: `node_modules/@mantine/core/esm/core/MantineProvider/MantineCssVariables/default-css-variables-resolver.mjs:22` mengisi `--mantine-scale: theme.scale` di `:root`.
- Kueri media tidak ikut skala (R11 T8, baris 29/332): benar secara standar CSS (`em` pada media query = ukuran font awal browser, bukan variabel CSS).
- **Temuan baru yang menyederhanakan R11:** breakpoint tata letak Mantine dibuat saat runtime dari `theme.breakpoints`: `MantineClasses.mjs:11-15` membangkitkan `.mantine-visible-from-*`/`.mantine-hidden-from-*` dengan `em(px(theme.breakpoints[bp]))`; `AppShellMediaStyles.mjs` memakai `InlineStyles` dari tema; prop responsif (`{base, sm}`, `cols`) juga lewat tema. `styles.css` inti hanya punya satu kueri lebar statis (`max-device-width: 31.25em`; 66 `@media` sisanya `hover`/`prefers-reduced-motion`), dan `app/` tidak punya `@media` sendiri maupun `postcss.config` (grep). Jadi `visibleFrom`, `hiddenFrom`, `AppShell navbar.breakpoint`, `SimpleGrid`/`Grid` ikut tergeser tanpa hook tambahan dan tetap benar saat SSR.
- Dampak pada 3 titik pindah sidebar → drawer (nilai `sm` AppShell, `AppFrame.tsx:40,122`): Normal: pindah di 768 px; Besar (×1,25): `sm`=60em ⇒ 960 px; Sangat besar (×1,5): `sm`=72em ⇒ 1152 px. Hasilnya: iPad 768/834/1024 tegak-mendatar dengan Besar masuk mode drawer di ≤ 960 (768, 834), sidebar penuh di 1024; Sangat besar: drawer di ≤ 1152 (768/834/1024), sidebar penuh di 1194. Lebar konten pada 1194 × 1,5: 1194 − 372 − 48 = 774 px (≈516 px setara Normal) memenuhi syarat "konten ≥ 480" milik R11 butir 2. (Perhitungan sendiri dari rumus R11 §3.7; breakpoint `md`/`lg` pada usul R11 tidak diperlukan.)
- Ukuran kontrol default Mantine (`styles/Button.css`, `Input.css`, `ActionIcon.css`): Button/Input `sm` 36 px, `md` 42 px, `lg` 50 px; ActionIcon `md` 28 px, `lg` 34 px, `xl` 44 px. Pada skala 1,5 `md` = 63 px.

**Alasan.** Satu mekanisme (tema) sudah menjamin portal/modal/toast ikut; skala 1,25/1,5 memberi jarak yang berarti bagi lansia (WCAG 1.4.4 mensyaratkan 200%), sedangkan 1,125 hanya +2 px. Menskalakan breakpoint menghapus hook `useTextSize().bp`, `useEffectiveWidth` untuk kasus ini, dan risiko lupa memakai `bp`. Alternatif ditolak: (a) `html{font-size}` / CSS `zoom` — tidak mengubah kueri media dan Mantine memakai `scale` (R11 butir alternatif c); (b) hook `bp` R11 — lebih banyak kode, hanya benar bila setiap komponen memakainya; (c) menimpa `--mantine-scale` pada `div` — token turunan sudah dihitung di `:root` dan portal di luar `div` (R08 baris 243); (d) 1/1,125/1,25 — kontras terlalu tipis.

**Konsekuensi.**
- `app/lib/theme.ts` (kini `createTheme({})`, 7 baris) → `buildTheme(scale)` + `TEXT_SCALE` (R11 §3 menyarankan memecah `theme-palette.ts`, `theme-components.ts`).
- `app/root.tsx`: loader membaca cookie, `buildTheme(TEXT_SCALE[size])`; `<html lang="en">` → `"id"` (root.tsx:46).
- Server (S0.a): `PATCH /api/app/me/profile` menulis `profile.text_size` dan `Set-Cookie: mk-text-size=…; Path=/; Max-Age=1y; SameSite=Lax` (cookie bukan rahasia). Login pertama tanpa cookie ⇒ baca `profile.text_size` di loader root bila sesi ada.
- Komponen yang memakai px tetap (242 `size={N}` di `app/`, sebagian ikon) hanya diperbaiki di berkas `/app` yang disentuh S1–S2; selebihnya risiko R-04.
- Tes: `tests/theme-scale.test.ts` (breakpoint ×skala, nilai default 1, enum tak dikenal ⇒ `normal`).
- Checklist uji R11 C04/C06 dijalankan pada tiga ukuran untuk setiap layar `/app` S1–S2.

**Dokumen yang diubah.** R08 §3 baris 243 (nilai 1/1,125/1,25 → 1/1,25/1,5; nama cookie); R11 §3.7 butir 1 (hook `bp` diganti breakpoint terskala) dan tabel 3 titik pindah; R05 §3 butir 6 (nama cookie); **R10 §3.3 S1 "Selesai bila"** (kalimat "diterapkan lewat `--mantine-scale` di `<html>`" → "lewat `theme.scale` dari cookie `mk-text-size` di loader root"). **Pemilik:** mekanisme tema + loader root = **S0.b** (kontrak beku); kolom `profile.text_size` + endpoint = **S0.a**. Perluasan ke `/dashboard`/`/dev` = ditunda.

### D5 — Gerbang 401 untuk `/api/app/**`
**Keputusan.** **Terima** usul R04 §3.1, dengan bentuk yang lebih sempit: gerbang 401 dipindah ke `derive` pada plugin bernama `appContext` (`server/api/app-context.ts`), yang `throw unauthorizedResponse(request)` (sebuah `Response` JSON berbentuk `{ error, code:'UNAUTHORIZED', status:401, requestId, method, path }`). Larangan baru: **jangan pernah `throw status(...)` di dalam `derive`** (jatuh ke 500). Gerbang status akun (pending/rejected ⇒ 403 `ACCOUNT_NOT_APPROVED`) dan pembatas tulis per-user tetap di `onBeforeHandle` pada plugin yang sama (butuh `actor`, dan urutan validasi→gerbang akun tidak membocorkan apa pun karena `actor` sudah terautentikasi). `index.ts` tidak disentuh.

**Bukti.**
- Perilaku sekarang: `server/api/app.ts:11-15` memakai `derive` + `onBeforeHandle` 401; R04 probe (§2.2, baris 46) menunjukkan POST anonim berbody salah ⇒ **422 + daftar isu skema**, bukan 401, karena validasi mendahului `onBeforeHandle`. Sedangkan probe baris 47: `derive` yang melempar `Response` 401 + `apiErrorPlugin` asli ⇒ 401 sebelum validasi, dan pengguna sah dengan body salah tetap 422 seragam. (Probe dijalankan R04, tidak kuulang karena dilarang menjalankan server; **ASUMSI**: hasil probe benar; spike 1 jam sebagai tes di S0.b memastikannya.)
- Penanganan: `server/api-error.ts:116` `if (error instanceof Response) return error;` di `onError` global ⇒ `Response` yang dilempar lolos apa adanya (tidak jadi 500). Karena itu `unauthorizedResponse` harus membangun JSON seragam sendiri, memakai `requestId` yang sama dengan `notFoundResponse` (R04 §3.1 baris 122).
- Kontrak hook di `CLAUDE.md` ("Urutan hook": `derive` di route berjalan pada fase transform, SEBELUM `onBeforeHandle` global; plugin yang menyuntik identitas memakai `onRequest`; urutan `apiErrorPlugin → rateLimitPlugin → maintenancePlugin → apiKeyPlugin → mount auth → router` adalah kontrak). Usul R04 **tidak melanggar** kontrak itu; justru memanfaatkannya: identitas kunci API tetap disuntik `apiKeyPlugin` lewat `onRequest` (`server/api/index.ts:79`) sebelum `derive` memanggil `resolveActor`. `appContext` wajib `.use`-d PERTAMA di `appApi` (hook induk hanya menjangkau rute yang didaftarkan sesudahnya; probe baris 45).
- R09 E7 (sapuan "anonim ⇒ 401 untuk setiap rute `/api/app/**`") hanya terpenuhi dengan pola derive (R04 K-C baris 56).

**Konsekuensi.**

### D7 — `timestamp` tabel user vs `timestamptz` tabel baru
**Keputusan.** (1) **Tidak ada konversi kolom lama.** Tabel milik Better Auth/fondasi (`user`, `session`, `account`, `verification`, `post`, log) tetap `timestamp` tanpa zona; semua tabel BARU dan kolom BARU (termasuk `user.approval_decided_at`, `profile.*`, `user_invitation.*`) memakai `timestamptz` (`timestamp(name, { withTimezone: true })`) lewat helper `schema.columns.ts` (R02 §3). (2) **Sesi koneksi dipaksa UTC**: `pgClient(dbUrl, { max: 5, connection: { TimeZone: 'UTC' } })` di `server/db/index.ts` (ASUMSI: opsi `connection` didukung `pgClient`; periksa saat implementasi) dan tes `SHOW TimeZone` = `UTC`. (3) **Larangan membandingkan kolom bertipe berbeda di SQL mentah** tanpa `AT TIME ZONE 'UTC'` eksplisit; mem-JOIN `user.created_at` dengan `task.created_at` harus lewat `(u.created_at AT TIME ZONE 'UTC')`. (4) Fragmen SQL mentah: tabel lama `${d.toISOString()}::timestamp` (aturan `CLAUDE.md`), tabel baru `::timestamptz` (R02 F3). (5) "Hari ini"/batas hari memakai `APP_TIMEZONE` (bawaan `Asia/Jakarta`, R08), dihitung server; kolom tanggal murni = `date` mode `string`.

**Bukti.** `server/db/schema.auth.ts:12-17` (`timestamp('created_at').$defaultFn(() => new Date())`, tanpa `withTimezone`); R02 F3 (baris 24) dan keputusan baris 52; `server/db/index.ts:20-22` membuat klien `postgres-js` tanpa opsi zona; brief: `timestamptz` untuk tabel baru. Drizzle memperlakukan `timestamp` tanpa zona sebagai UTC saat memetakan (`mapFromDriverValue` menambah `+0000`; **ASUMSI** dari pengetahuan drizzle-orm 0.45, tidak dibuka), sehingga aplikasi konsisten selama zona sesi PG = UTC; perbandingan lintas-tipe di SQL memakai zona sesi dan bisa bergeser bila tidak UTC.

**Alasan.** `auth.schema.ts` dibangkitkan ulang oleh `bun run auth:generate` (`package.json:28`) dengan `timestamp` tanpa zona, jadi mengubah tipe kolom Better Auth akan terhapus pada regenerasi dan berisiko pada migrasi data produksi. Memaksa zona UTC menutup satu-satunya risiko nyata (perbandingan lintas-tipe). Alternatif ditolak: (a) migrasi semua kolom lama ke `timestamptz` — risiko tinggi, tanpa manfaat bagi S0–S2; (b) membuat tabel baru `timestamp` tanpa zona agar seragam — melanggar brief dan menyulitkan fitur zona waktu (Events); (c) mengandalkan zona server — tidak deterministik di PG lokal tertanam vs eksternal.

**Konsekuensi.** `schema.columns.ts` (S0.b) menyediakan `createdAt()/updatedAt()` bertipe tz; kolom "nama sama beda tipe" pada `user` vs `profile` didokumentasikan di komentar skema ("kenapa", aturan §4); dua `test` baru: zona sesi UTC, dan integrasi `user.created_at` vs `task.created_at` pada DB test dengan `SET TIME ZONE 'Asia/Jakarta'` di satu koneksi yang diharapkan tetap benar saat memakai `AT TIME ZONE 'UTC'`. **Dokumen:** R02 §3 (catatan konvensi), `CLAUDE.md` (D9 butir 6). **Pemilik: S0.b.**

### D10 — Scope API key untuk data PM (`PM_KEY_DENY`)
**Keputusan.** **Terima** opsi C R04 §3.3 (dua scope `app:read`/`app:write` + daftar tolak) dengan dua perubahan: (1) untuk S0–S2 daftar tolak hanya memuat rute yang BENAR-BENAR ada; pola untuk rute S3+ ditambahkan bersama rutenya (tes R04 "tiap pola cocok ≥1 rute nyata" akan merah bila tidak); (2) tiga prasyarat fondasi dipindah ke S0.a karena tanpa itu daftar tolak tidak berarti.
- **Daftar S0–S2:** `DELETE /api/app/projects/*`; `* /api/app/projects/*/members*`; `PATCH /api/app/profile`; `* /api/app/avatar`. **Ditunda (satu baris):** `…/tasks/*/approve|return` (S4), `…/attachments`, `/api/app/files/*` (S5), `DELETE /api/app/trash/*`, `PUT /api/app/team-settings` (S6).
- Kunci API tetap boleh: baca semua yang boleh dilihat pemiliknya, serta tulis rutin (buat/ubah tugas, komentar, checklist, transisi start/selesai, hapus-ke-Sampah tugas yang bisa diurungkan). Kunci selalu bertindak sebagai pemilik; IDOR proyek orang lain tetap 404.
- **Prasyarat S0.a:** (i) `ROLE_RANK` di `server/api-keys/scopes.ts:122` (`{ user:0, admin:1, 'super-admin':2 }`) diisi empat role dan `minRole: ROLES.USER` → `MEMBER` (tanpa itu kunci PM gagal-tertutup, R12 F12); (ii) jalur kunci menolak pemilik berstatus `pending/rejected/suspended` — `server/api-keys/plugin.ts:106` kini hanya memeriksa `owner.banned` (R12 F5); (iii) `app:write` tidak pernah melewati `PM_KEY_DENY`.

**Bukti.** `server/api-keys/scopes.ts:166` — `if (p.startsWith('/api/app/') || p === '/api/app') return read ? 'app:read' : 'app:write';` (semua non-GET di `/api/app` otomatis `app:write`, termasuk menyetujui/menghapus/mengubah anggota); `scopes.ts` 190 baris (batas config 100 ⇒ tidak boleh ditambah), sehingga R04 menaruh daftar di berkas baru `server/api-keys/scopes.pm.ts` (≤50 baris) dan `requiredScope` memanggil `isPmKeyDenied(method, path)` sebelum baris 166 (+3 baris). R04 menolak opsi A (kunci bisa menyetujui tugas ⇒ pemisahan pemeriksa runtuh bagi skrip/agen) dan opsi B (±14 scope, +84 baris). `plugin.ts:100-110`: pemeriksaan pemilik hanya `OWNER_MISSING`, `owner.banned`, `roleAllowsScope`. `CLAUDE.md` Konvensi Server: rute API baru wajib dipetakan di `scopes.ts` + assertion di `tests/api-keys/scopes.test.ts`.

**Alasan.** Keputusan manusia (menyetujui), eskalasi hak (anggota) dan hapus proyek tidak patut dijalankan skrip yang kuncinya bisa bocor; scope per fitur (opsi B) mahal tanpa manfaat karena izin sebenarnya dihitung dari `Principal`. Mengurangi daftar ke rute yang ada menghindari pola mati dan stub (aturan §17). Alternatif ditolak: A (tidak aman), B (mahal), menolak SEMUA akses kunci ke `/api/app` (menghilangkan nilai OpenAPI untuk agen/skrip).

**Konsekuensi.** Tes: `tests/api-keys/scopes.test.ts` +assertion tiap baris tolak (4) + 2 rute W + 2 rute R; tes sapuan "tiap rute `api.routes` berprefiks `/api/app/` punya `requiredScope` non-`undefined`" (R04 §3.3); rute `null`/ditolak otomatis hilang dari spec OpenAPI kunci (`openapi.ts:34-37`). `PATCH /profile` dan `/avatar` yang dulu bisa diakses kunci kini 403 — perubahan perilaku kecil yang dicatat di CHANGELOG `Changed`. **Dokumen yang diubah:** R04 §3.3 (daftar tolak per irisan), README bagian API key, `CLAUDE.md` Konvensi Server (D9 butir 8c). **Pemilik:** S0.a (prasyarat i–iii), S0.b (`scopes.pm.ts` + tes), tiap irisan menambah barisnya sendiri.
